## 2. ① 全下载：工程代价与实现路径

### 2.1 核心判断：同步等待不可行，必须两段式

`t_dl ≈ 6.5 s × 视频分钟数`（实测 163 KB/s、0.36 Mbps 的线性外推）。群里发一个 20 分钟的视频，全量同步下要 2 分 10 秒才开口；1 小时要 17 分钟。QQ/微信侧「等两分钟才回」等于失败。

**结论：`watch_mode = "two_phase"`（默认）**

```
t=0     收到链接
t≈0.3s  元数据（--dump-single-json：标题/UP/简介/时长/有无 cc 字幕轨）
t≈8s    Phase A：下前 300 秒 → 抽帧 → 字幕（若可得）→ 立刻回一段
        → 明确前缀「我先看了开头 5 分钟」
t≈9s    起后台 job：Phase B 全量下载 + 字幕 + 抽帧计划
t≈7min  job 完成 → 追加一条「后面那段我也看完了：…」+ 帧/字幕落档
```

分流判据（写进代码，不靠模型判断）：

```
t_dl_est = 6.5 * (dur_sec / 60)
if dur_sec <= 780 (13min) and t_dl_est <= 90:   watch_mode = "full_sync"
else:                                            watch_mode = "two_phase"
```

短于 13 分钟的片子直接全量同步（下载 ≤ 90 秒，还能接受）；长片走二段。

### 2.2 为什么不是「续下」

`--download-sections "*0-300"` 产出的是**被 ffmpeg 重切过的独立文件**（时间轴从 0 开始、容器已收尾），拿不到原始 DASH 分片偏移，所以**不能把后 2700 秒接到它后面**。

两条可行替代，取舍如下：

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| A（推荐） | Phase A 用 `*0-300` 出 `preview.mp4`；Phase B **另起一次全量下载**出 `full.mp4`，Phase A 产物在 B 完成后作废 | 白下约 5–15 MB、白花 ~10 秒 | ✅ 唯一稳妥，且 A 的产物还能进缓存给「快速回看」用 |
| B | Phase B 只下音频（`bestaudio`）+ ASR | 见 ⑤ 第 3 级，ASR 未实测 | 留作以后 |

**不要**为了「续接」去拼 DASH 分片：签名 URL 会过期、序号与 `Sidx` 需要自己算，失败率高、维护成本远大于省下的 10 秒。

### 2.3 并发与超时（这一块必须显式设计，否则多群同时发链接会互相拖死）

1. **全局下载闸门**：`watch_slots = 1`（`asyncio.Semaphore` 放在跨插件共享的 kit 层，因为 `feiyu_explore` 也在下视频）。抢不到锁时不排队死等，直接回「上一个视频还在下，等我这个看完」。
2. **两段不同的超时语义**：
   - Phase A：`subprocess timeout=120`（现有值够用，实测 8.6s）。
   - Phase B：**不用 subprocess timeout**（会误杀长下载），改两件套：
     - 停滞看门狗：每 30 s 读一次 `.part` 大小，**180 s 零增长**即杀进程 → 降级；
     - 墙钟上限：`download_deadline_sec=900`（15 分钟，覆盖 1 小时片的最坏情况）。
3. **磁盘水位闸门**：起下载前检查剩余空间 `< disk_free_min_mb=2048` 直接拒，并明说「磁盘不够了」。
4. **清理**：每个 task 一个目录 `data/plugin_data/astrbot_plugin_feiyu_video/tmp/<taskid>/`，结束即删；`initialize()` 里扫掉 >6h 的残留目录。
5. **缓存**：key = `{bv}_{height}_{sections}`，落 `cache/<key>.mp4` + `<key>.json`（含 dur、bytes、mtime、subs 是否存在）。TTL 10 分钟。命中即复用 —— 她经常「再看一遍」「刚才那个第 3 个是什么」，命中率高、几乎白送。

### 2.4 时长/体积校验（没有 ffprobe 的现实）

- 时长：沿用 `main.py:737` 解析 `ffmpeg -i` 的 `Duration:`，不引新依赖。
- 完整性：`bytes >= 0.8 * 期望字节`（期望字节 = `dur_sec × 目标码率`），或用「ffmpeg 全片 decode 到 null 的成功退出」当校验（实测 25 分钟片 7 秒即可完成，可接受）。
- **不要用 `--max-filesize`**：历史坑（大文件会静默失败）。

### 2.5 需求 1 的落地措辞

「全下载」在实现上 = **不再有 300 秒的内容裁剪**，`ytdlp_seconds` 退化为「首段预览长度」。`max_seconds=3600` 保留为**内容时长闸门**（超过 1 小时的视频拒绝并说明），**不再当下载配额**。

## 3. ② 信息密度：怎么量化

### 3.1 信号清单与取舍

| 信号 | 可计算性 | 实测/估算成本 | 采用 |
|---|---|---|---|
| 字幕 cue 字数密度 | 直接算 | 0 | ✅ 主信号 |
| cue 边界间隔（说话节奏） | 直接算 | 0 | ✅ 折进主信号（过短/过长 cue 降权） |
| 数字 / 拉丁词 / 书名号 / 因果词 | 正则 | 0 | ✅ 加分项 |
| 切镜分数（画面变化） | `ffmpeg select=gt(scene,T)` | **全片 7.3s** | ✅ 全片扫，不抽样 |
| 音量/RMS 峰值 | ffmpeg `volumedetect` 全扫 | 需再跑一遍（估计 5–10s） | ⭕ v2.1 备选 |
| 弹幕峰值 | 有 xml | — | ❌ **不用**（约束：danmaku 不是内容） |
| 光学流/嵌入相似度 | 太重 | 分钟级 | ❌ |

### 3.2 主公式

把时间轴等分成 `n = frames` 个桶，桶宽 `w = dur / n`。

```
cue_chars_i   = 落在桶 i 内的字幕字数（按 cue 与桶的时间交集长度加权）
cue_rate_i    = cue_chars_i / w                      # 字/秒
events_i      = 桶内 cue 条数 / w                     # 条/秒（说话切换频率）
keyword_i     = 桶内命中词表次数（数字/拉丁/书名号/因为所以/第一/原理/步骤/结论…）
cut_i         = 桶内切镜次数（scene 分数 > scene_threshold 的帧数）

S_i = 0.50 * z(cue_rate_i)
    + 0.15 * z(events_i)
    + 0.20 * z(keyword_i)
    + 0.15 * z(cut_i)
```

`z()` = 稳健标准化（`(x - median) / (MAD * 1.4826)`，MAD 为 0 时退化为 min-max，全等时全 0）。

**退化规则（这是 ② 的核心接口）**：

| 可用信号 | 权重调整 |
|---|---|
| 有字幕 + 有切镜 | 0.50 / 0.15 / 0.20 / 0.15 |
| 有字幕 + 无切镜 | 0.58 / 0.17 / 0.25 / **0.00** |
| 无字幕 + 有切镜 | **0.00 / 0.00 / 0.00 / 1.00**（纯画面变化） |
| 都没有 | **退化为等间隔** `t_i = dur*(i+0.5)/n`（即现状），并在 note 里标注 `plan="uniform"` |

### 3.3 覆盖约束（否则「高密度」会把 30 帧全挤在同一段演讲里）

```
anchors = 均匀取 ceil(n * density_anchor_ratio) 个桶（默认 0.5 → 15 个）
rest    = n - len(anchors)
elected = []
for b in buckets 按 S_i 降序:
    if b in anchors: continue
    if 与已选桶的时间距离 < 2*w: continue      # 最小间距，防扎堆
    elected.append(b)
    if len(elected) == rest: break
选中桶 = anchors ∪ elected
```

每个选中桶里的**具体取帧时刻**：
- 有字幕：桶内 cue 字数最多的那条 cue 的中点（**帧和台词对得上**，她引用原话时不会说错）。
- 无字幕：桶中点。

### 3.4 接口形状（`_frames_from_url` 的改造）

现状 `(frames, note)` —— 缺三样东西，导致 ②④ 都做不了。改成：

```python
{
  "frames": [ "/abs/f1.jpg", ... ],          # 路径列表（stdout 兼容）
  "note":   "人话一句（内部/日志/降级用）",
  "plan": {                                   # 纯数据结构，可落盘可缓存
     "mode": "density" | "scene" | "uniform",
     "dur": 1541.0,
     "items": [
        {"idx": 1, "t": 83.2, "src": "density",
         "cue": "所以说这个机制的核心是…",     # 该刻附近的字幕原文；无字幕为 None
         "scene": 0.41},
        ...
     ],
     "signals": {"subs": true, "scene": true, "chars": 6120},
  },
}
```

`note` 给人（日志/降级话术），`plan` 给机器（注入模板、时间戳申请、补帧）。**`note` 里不准出现签名 URL**（沿用现有 `_user_hint` 分层）。

### 3.5 需求 2 的落地措辞

「根据字幕信息密度截帧」= `S_i` 主项是字幕密度；「无字幕时默认（等间隔）抽帧」= 上表最后一行。两条都在 `plan.mode` 里留痕，方便以后统计命中率。

## 4. ③ 预算：全文但不炸上下文

### 4.1 基数估算（先算清楚再设计）

中文口播 4–5 字/秒 ⇒ 25 分钟片 **6000–7500 字**，1 小时片 **15000–18000 字**。字幕（cue 级、带换行与重复断句）比纯文本更胖，乘 1.2 ⇒ 1 小时片 **约 2 万字符**。

上下文现状：人格 5589 + 能力块 310–467 + 工具卡 250 + 最近对话。把 2 万字塞进当轮 user 消息的后果是**它变成永久历史**（每轮重算，20 轮后上下文爆），这是必须避开的。

### 4.2 设计：正文落文件，当轮注入一次

```
1) 下载字幕 → 规范化 → 落 data/plugin_data/.../subs/<vid>.txt
   每行格式：[mm:ss] 台词原文
2) 当轮注入（一次性，不落库）：
   TextPart(.....).mark_as_temp()      # 依据 core/agent/message.py:350-355
3) 注入文本 = 输出契约 + 标题/UP/简介(截断) + 帧表(#n / 时刻? / 画面描述) + 字幕正文(按预算分级)
```

`mark_as_temp()` 等价于 `part._no_save=True`，`see_frames_with_llm`（`main.py:650`）已经在用这个机制塞图片，字幕沿用同一套，**不新增通道**。

### 4.3 三级预算（按字符数，保守当 token 算）

| 字幕字符数 | 注入策略 | 帧数 | 说明 |
|---|---|---|---|
| ≤ `subs_full_chars=8000` | **全文注入**，一字不删 | 10 | 覆盖 10 分钟以内的片子 |
| 8000–20000 | **全文注入**，帧数减半 | 6 | 字幕本身信息够，画面只做锚点 |
| > 20000 | **分段注入**：按「与 question 的关键词重合度」挑 3 段 + 首尾各 1 段，段间用 `…（省略 N 分钟）…` 标出；正文一字不改 | 4 | **这不是摘要**，是分段；且注入里明说「我只念了你问的部分，要看别处就说」 |

> 关键区别：需求 3 禁止的是**摘要**（改写/压缩语义），不是禁止**分段**。分段后每段仍是原文，且她可以按需索取其余部分（§8 的「回看」动词）。

### 4.4 图片预算（被忽略的另一半）

`see_shots=30` 一次塞 30 帧 640px 图 ≈ 30 × ~1.1k token ≈ **33k token/轮**，比 8000 字字幕还贵。v2 改为：

- `see_shots=10`（默认），`frames_total` 仍 30（抽出来备着，落盘）。
- **拉取式补帧**（对称于时间戳申请）：她若追问「2 分 30 秒那个画面」，走同一动词 `question="2分30秒那幅图再给我看看"`，命中时间正则 → **只对那一处临时抽 1–3 帧**再注入（`-ss` 快 seek，0.22s/帧，几乎免费）。这样「看到多少」变成可控、可追问，而不是一次性 30 张。

## 5. ④ 时间戳：存取协议

### 5.1 默认不给（结构上不给，而不是靠自觉）

注入文本里的帧表长这样：

```
画面（我先看的这 10 个点）：
  #1  开头，黑底白字标题「……」
  #2  一个人坐在桌前讲，手边有……
  #3  屏幕上出现一张流程框图……
```

**没有「0:12」「第 83 秒」这种数字**。所以「别暴露时间戳」不需要提示词去守、也不需要后处理去洗 —— **她手上根本没有这个数**。这是唯一不会随时间漂移的守法和最短的一条路。

### 5.2 要的时候怎么申请

**不新增参数、不新增动词**，用现成的 `question`：

```
feiyu(action="看视频", target="<URL>", question="第 3 个是什么，在几分几秒")
```

判定（在 handler 里，纯正则，不依赖模型）：

```python
_WANTS_TIME = re.compile(r"几分|几点|多少秒|第几秒|时间|时点|多久|哪一秒|哪个位置|从哪开始|直接看|跳到|定位")
_WANTS_REF  = re.compile(r"第\s*[一二三四五六七八九十\d]+\s*(个|张|幅|段|处)|再给我看|截图|那一帧|这个画面")
```

- 命中 `_WANTS_TIME` → 回答里附 `#3 = 01:23`，**并且**给 B 站可点链接 `https://www.bilibili.com/video/{BV}?t=83`（这才是「主人想去看时一下找到」的答案；纯 `01:23` 他还要自己拖）。
- 命中 `_WANTS_REF` → 临时抽该处 1–3 帧补进当轮（§4.4）。
- 两者都不命中 → 保持「只给编号」。

为什么不用新参数：`feiyu(action, target, text, question)` 是工具 schema 的一部分，加字段会改工具卡（250 字预算）并且正好踩 `context/handler/method_name` 保留字风险区；而 `question` 语义本来就是「你要问的东西」，天然容纳「几点」。

### 5.3 「别暴露」三层责任

| 层 | 做法 | 是否必须 |
|---|---|---|
| 结构层（主） | 默认注入里没有绝对秒数 | ✅ |
| 措辞层（辅） | 注入末尾一句硬约束：「这些编号不是你看到的时间，别自己换算成几分几秒」 | ✅ 一句话，成本 0 |
| 后处理层 | **不做**正则替换 | ❌ 会把「我等了 3 秒」也洗掉，脆弱且不可解释 |

## 6. ⑤ 主路由与降级顺序

```
L1  B 站 AI 字幕（player/wbi/v2 → subtitle.subtitles[]，lan 含 ai-zh / zh-Hans）
      需要登录态。实测当前 cookies 全部过期 → 现在这一步必然是 fail，必须先修登录
L2  yt-dlp --write-subs --write-auto-subs --sub-langs "ai-zh,zh-Hans,zh,zh-CN"
      （同样吃 cookies；把 L1 的 curl 直连换成 yt-dlp 的封装）
L3  L1/L2 都空 → 判定「这片子没有可用字幕」
      → 抽帧退 scene/uniform 模式（§3.2 退化表）
      → 回答里必须明说「这视频没有字幕，我是看画面说的」（需求 5）
L4  连帧都没有（下载失败 / ffmpeg 挂 / 视觉模型超时）
      → 只凭标题/UP/简介说
      → 回答里必须明说「画面没看到」（需求 4）
L5  （可选，本期不做）音频 ASR：下 `bestaudio`（1h ≈ 28.8 MB ≈ 2.5 分钟）+ faster-whisper
      环境无 faster-whisper，转写速度未实测，先留接口 subs_source="asr" 不实现
```

**"字幕格式白名单"必须写在解析处**（呼应「不碰弹幕」）：只接受 `json3 / srt / ass / vtt` 解析器，且 `--sub-langs` 与文件名里出现 `danmaku` 的一律跳过。B 站 `subtitles` 字段里永远躺着弹幕 xml，不设白名单就会把弹幕当台词念出来。

**L1 前置条件（必须先解决的现实问题）**：`~/.bili-ai/credentials.json` 与 `D:/qqaibot/bili_cookies.txt` 都过期。修法二选一：
1. 用主人在用的浏览器登录 B 站后，用扩展导出 `cookies.txt` 覆盖 `D:/qqaibot/bili_cookies.txt`（推荐：稳定、可版本化）；
2. 改走 bsk 无头会话（项目里 feiyu_comment 已经在用页面同源 fetch，能直接带 `bili_jct`）——**这条更稳**，因为不依赖手工导出，代价是每次多一次页面打开（~3s）。

建议：**v2 主路由直接走 bsk 页面同源 fetch**（复用 feiyu_comment 的登录判定：`x/space/myinfo` code=0 或 cookie 里有 `bili_jct`），而不是 curl + cookies.txt。这样「登录失效」从「静默降级到没字幕」变成「明确报一句她的话术」。

## 8. 输出契约（需求 4/5/6 的落地文字）

注入文本的骨架（一次性 temp part）：

```
【这次看的是】{标题}｜{UP}｜{时长}
【字幕】{有：以下为全文，未改写 / 无：这视频没有字幕，只有画面}
【画面】{有：下面 10 个点我看到了 / 无：画面我没看到，只能凭标题和简介说}
#1 ……（#n 只是顺序号，不是时间）
【怎么说】只讲具体的：谁、做了什么、说了哪句话、出现了什么、数字是多少。
  不写「很有意思」「值得一看」「整体不错」这类评价。没看到的就说没看到。
  #n 不要换算成几分几秒去说；他问时间你再给。
```

需求 6「文本只输出具体信息」的验收样例：

- ❌「这个视频讲的是深度学习里的一种注意力机制，非常有启发性，值得一看，建议你去看原片。」
- ✅「他演示的是一个叫『多头注意力』的东西：输入切成 8 份各自算一遍再拼起来，8 这个数字他重复了三次。第 4 个画面里出现了一张 4×4 的表，左上角写着 Q·K。」

需求 4/5 的**结构强制**（不靠模型自觉）：`plan` 里带 `vision: bool` 与 `subs: bool`，注入模板按真值选句子；两者同时为假时模板里出现的是「画面没看到」这句固定话术，模型没有别的可抄。

## 9. 取舍与 ADR 摘要

### ADR-001：全下载用「两段式」，不做流式续接
- 背景：实测 163 KB/s，1 小时片要 17 分钟；`--download-sections` 产物不可续。
- 决定：Phase A 前 300 秒同步、Phase B 全量后台、完成后补一条。
- 代价：白下约 5–15 MB（≈10 秒）；两次进程启动；状态机多一个 `phase` 字段。
- 收益：首句延迟保持 ~9 秒（现状水平），同时满足「全下载」。

### ADR-002：时间戳「结构上不给」，按需申请
- 背景：需求 7 既要「重要」又要「别暴露」，还要求「她之后能申请到」。
- 决定：默认注入无绝对时间；`question` 命中正则才给 `#3 = 01:23` + `?t=83` 链接。
- 代价：她要主动问；`?t=` 链接对非 B 站源无效（此时只给 `01:23`）。
- 收益：不需要提示词守、不需要后处理洗、不会因为模型换版本而漏。

### ADR-003：字幕全文 + 分段，不做摘要
- 背景：需求 3 明确「不做摘要」；但 1 小时片 2 万字会爆上下文。
- 决定：正文落文件；当轮 temp 注入按 8k/20k 三级；超出则**分段**（保留原文）而非摘要。
- 代价：超长片她要再申请才能看全（多一轮）。
- 收益：她引用的永远是原话；上下文成本可控且可见。

### 备选方案与被否理由

| 备选 | 否掉的理由 |
|---|---|
| 一次同步全量下载 | 长片 17 分钟才开口，体验不可接受 |
| 用 DASH 分片续接 | 签名 URL 过期 + Sidx 自算，失败率高 |
| 字幕先摘要再注入 | 违反需求 3；且摘要会丢她要复述的细节 |
| 把时间戳写进注入了再提示词禁止暴露 | 模型换版本/长对话后容易漏，不可验证 |
| 弹幕当内容 | 违反约束；弹幕是观众反应，不是视频内容 |
| `--max-filesize` 控体积 | 历史坑：大文件静默失败 |
| 本地 ASR 当主路由 | 环境无 faster-whisper，转写耗时未实测，风险不可控 |

## 10. 风险与待验证

| 风险 | 影响 | 缓解 |
|---|---|---|
| **B 站登录态过期**（当前就是） | L1/L2 全失效，退回「无字幕」 | 主路由改 bsk 页面同源 fetch；失败时明确话术，不静默 |
| 163 KB/s 是否长期稳定 | 1h 片 17 分钟 vs 更慢 | 停滞看门狗 + 墙钟上限 + 明说「还没下完」 |
| 字幕字符率未知（无样本可测） | 8k/20k 阈值可能偏 | 首次运行记录 `chars/dur`，一周后按实测调 |
| 密度抽帧是否真的更好 | 可能不如等间隔直觉好 | `frames_by_density` 开关 + 日志记 `plan.mode`，可比对 |
| 视觉模型超时（`see_timeout=90`） | 30 帧塞不进去 | see_shots=10 + 拉取式补帧 |
| 图片 token 计入 | 每轮成本 | 已在 §4.4 量化 |
| ASR 路线 | 未实测 | 留接口默认关 |

**验证清单（实现后按此验收）**

1. 25 分钟片：`t_first_reply ≤ 15s`，Phase B `≤ 10min`，追加消息到达。
2. 有字幕片：`plan.mode == "density"`，帧与台词对得上（抽 3 帧人工核对）。
3. 无字幕片：`plan.mode` ∈ {`scene`,`uniform`}，回答里出现「没有字幕」。
4. 下载失败：回答里出现「画面没看到」，且不含任何签名 URL。
5. 问「第 3 个几分几秒」：回答带 `#3 = 01:23` 与 `?t=83`；不问则不带任何 `mm:ss`。
6. 1 小时片：注入字符数 ≤ 20000，且 `no_save_parts` 生效（下一轮上下文不重放字幕）。
7. 并发两个群同时发链接：第二个拿到「上一个还在下」的话术，不超时错乱。
8. 弹幕文件存在时：解析器不读它（`*.danmaku.*` 白名单外）。
